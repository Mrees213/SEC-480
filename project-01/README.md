# Project 1

## Subject

This project analyzes a small PowerShell script derived from previous cybersecurity lab work.

The script configures and queries Windows process auditing settings and includes a query for Event ID 4688.

The artifact was intentionally kept small enough to inspect completely and analyze line by line.

## Analysis Question

> What Windows auditing behavior does this PowerShell script explicitly configure or verify, and what cannot be determined from the script alone?

## Planning and Tracking

Project work was tracked using GitHub issues and a milestone.

A definition of done and an output contract were written before the analysis was performed.

Project instructions were also tested through a verbatim read-back. The instructions themselves were returned correctly, although Claude also repeated the read-back prompt after them.

## Evidence Analysis

The PowerShell source artifact was analyzed using three claim categories:

- stated
- inferred
- unsupported

The analysis showed that the script explicitly configures Process Creation auditing and modifies the `ProcessCreationIncludeCmdLine_Enabled` registry value.

It also contains commands that query those settings and retrieve Event ID 4688 records.

However, the source code alone cannot prove that the script was executed successfully, that the expected events were generated, or that command-line data actually appeared in those events.

The critique also identified several cases where the AI analysis went beyond the supplied evidence, including repository information and claims about returned event ordering.

## Reusable Skill

A reusable Evidence Review Skill was created to analyze supplied artifacts using the same evidence discipline.

The Skill requires:

- a supplied artifact
- an analysis question
- claims classified as stated, inferred, or unsupported
- exact supporting evidence
- `NO EVIDENCE` for unsupported claims
- a `Cannot determine from this evidence` section

## Skill Reuse Test

The Skill was reused without modification on a different artifact type: a Dockerfile.

The second analysis question was:

> What application environment and startup behavior does this Dockerfile explicitly define, and what cannot be determined from the Dockerfile alone?

The Skill successfully analyzed the Dockerfile and identified explicit behavior such as the base image, working directory, dependency installation command, exposed port, and startup command.

The reuse test also showed that the Dockerfile alone could not establish whether the application actually listens on port 5000, whether `app.py` exists, what dependency versions are installed, or whether the image builds successfully.

Claude introduced some surrounding repository and branch information outside the Dockerfile evidence, but the evidence-review method itself still transferred successfully to the second artifact.

## Cross-System Chain

The Project 1 cross-system chain used:

Google Drive → Claude → GitHub

A prediction was written before the chain was tested.

The source file contained:

> Project 1 evidence review completed.  
> The PowerShell artifact was analyzed using stated, inferred, and unsupported claims.

Claude successfully read the file from Google Drive and created GitHub issue #16, `Project 1 analysis handoff`.

The visible source text transferred correctly, but the GitHub integration automatically added a divider and a `_Generated by Claude Code_` footer that was not present in the source file.

The Drive export also contained a byte-order mark and Windows-style line endings that were normalized during transfer without changing the visible text.

This supported the prediction that a cross-system task could report success while still changing the destination content.
