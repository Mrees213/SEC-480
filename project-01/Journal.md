# Project 1 Journal

Project 1 focused on applying the evidence-review method from Module 3 to a new artifact, turning that method into a reusable Skill, and testing a cross-system workflow.

For the main artifact, I used a small PowerShell script based on previous cybersecurity lab work. The script configures Windows process-creation auditing, modifies the `ProcessCreationIncludeCmdLine_Enabled` registry value, queries those settings, launches a small test process, and then queries the Security log for Event ID 4688.

Before running the analysis, I created a definition of done and an output contract. I also created Project instructions that required claims to be separated into `stated`, `inferred`, and `unsupported` categories and required unsupported claims to use `NO EVIDENCE`. I tested those instructions with a read-back prompt. Claude returned the instructions correctly, but it also repeated the read-back prompt itself, which showed that even a simple instruction test can include extra output.

The analysis question was:

> What Windows auditing behavior does this PowerShell script explicitly configure or verify, and what cannot be determined from the script alone?

Claude correctly identified several direct behaviors in the script, including enabling Process Creation auditing, setting the command-line logging registry value, querying those settings, launching a test process, and retrieving Event ID 4688 records.

The critique also showed several places where the AI went beyond the evidence. For example, the script did not prove that the returned Event ID 4688 records belonged to the test process, did not prove that command-line text was actually captured, and did not prove that the commands successfully executed. Claude also introduced repository and branch information that was outside the supplied PowerShell evidence. This reinforced the need to separate what the artifact actually proves from what seems likely or plausible.

I then turned the evidence-review method into a reusable Skill. The Skill required a supplied artifact and an analysis question, classified claims as `stated`, `inferred`, or `unsupported`, required exact evidence, and ended with a `Cannot determine from this evidence` section.

To test reuse, I applied the same Skill to a completely different artifact: a Dockerfile. I did not change the evidence-review procedure. The Skill successfully identified explicit Dockerfile behavior such as the Python base image, working directory, dependency-installation step, exposed port, and startup command. It also correctly identified what could not be established from the Dockerfile alone, such as whether the application actually listens on port 5000, whether `app.py` exists, what package versions are installed, or whether the image successfully builds. The reuse test showed that the method was not limited to PowerShell or Windows auditing.

The final part of the project was a cross-system chain using Google Drive, Claude, and GitHub. I wrote a prediction before the test that the information would probably cross successfully but might be changed at the destination. The source file in Google Drive contained a short Project 1 handoff message. Claude read the file and created GitHub issue #16 with the expected text.

The chain succeeded, but the destination was not an exact copy of the source. The GitHub connection automatically added a `_Generated by Claude Code_` footer, and an attempt to remove it caused it to be added again. The Drive export also contained a byte-order mark and Windows-style line endings that were normalized during the transfer. The visible text remained the same, but the destination still contained extra generated content.

The main lesson from Project 1 was that successful automation and convincing analysis are not the same as verified correctness. The PowerShell analysis showed that AI can produce reasonable explanations while still introducing unsupported claims. The Skill reuse test showed that a well-defined evidence-review method can transfer to a different artifact. The cross-system chain showed that even when information moves successfully between systems, the final destination still needs to be checked directly.

Overall, the project reinforced the importance of defining expectations before starting, separating evidence from inference, testing reusable methods on different inputs, and verifying results at the final destination instead of trusting success messages alone.
