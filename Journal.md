# Module 3 Journal

Module 3 focused on planning work before starting it, connecting a second system, building a task that crossed between systems, and checking AI-assisted analysis against the actual evidence.

The first major difference from the previous modules was that the planning had to come before the work. I created issues for each act, attached them to `Milestone_01`, and used those issues to track the work instead of documenting everything afterward. This made the difference between a plan and a record much clearer. A plan can turn out to be wrong and show where work is falling behind, while a record written afterward only describes what already happened.

For the second-system portion, I connected Google Drive and tested the connection in both directions. I confirmed that the platform could read a file I placed in Drive and that it could also write information back into Drive. This was more useful than simply seeing that the connection was authorized because it verified that information could actually move through the integration.

For the cross-system chain, I used Google Drive as the source and GitHub as the destination. I created a small text file in Drive, had Claude read it, and then asked Claude to create a GitHub issue using the same content. The chain worked, but the result was not an exact copy of the source because the GitHub integration automatically added a `_Generated by Claude Code_` footer. Even after Claude attempted to remove it, the footer was added again. This was a good example of the crossing point problem from the module. Both systems technically worked, but the information changed during the handoff. Verifying the result directly in GitHub showed something that the success message alone would not have revealed.

The investigation was the most important part of the module. The evidence packet contained the incident ticket, file-system audit log, chat export, and asset record. The question was whether the evidence could establish who removed `\finance\Q3-working` and when it disappeared.

The evidence supported a time range but not an attribution. The folder was still present at 08:31:19 on September 14, when `mreyes` successfully read `notes.docx` from inside it. By 13:15:11, an attempt to access `Q3-working` failed with `PATH_NOT_FOUND`. This means the evidence can establish that the folder disappeared sometime after 08:31:19 and before 13:15:11.

The main limitation was the audit gap. Object-access auditing was disabled at 08:58:41 and was not restored until 13:04:12. The log explicitly warned that the gap should not be treated as a period of inactivity. Because most of the disappearance window overlaps this gap, it is reasonable to infer that the removal may have happened during that period, but the evidence cannot prove it.

The evidence also showed why it was important not to accept a confident explanation too quickly. `jcontractor` was on fs02 performing cleanup work and later said that old material had been cleared, which makes the contractor relevant to the investigation. However, the asset record lists the contractor group with Read access to `Q3-working`, and no supplied record actually shows the contractor deleting or moving the folder. Similarly, the finance team had Modify access and Domain Admins had Full access, but permissions only establish capability, not responsibility.

One part of the AI analysis also needed correction. It originally said that Dana's statement that she opened the file Monday afternoon conflicted with the machine evidence. That was too strong because auditing remained disabled until 13:04:12. An afternoon access between noon and 13:04 could have happened without appearing in the audit log. The better conclusion was that Dana's recollection was unconfirmed, not disproved.

The final result was that the evidence could answer part of the ticket but not all of it. The evidence could establish a bounded disappearance window, but it could not establish who removed the folder, the exact removal time, or whether it was deleted, moved, or renamed.

The main lesson I took from Module 3 was that a system saying an action succeeded is not the same thing as proving the intended result happened. That applied to the Drive-to-GitHub chain, where the content changed during the handoff, and it also applied to the investigation, where a plausible-looking explanation was not the same thing as a supported conclusion. The most useful habit from this module was separating what the evidence directly states from what can only be inferred, and being willing to say when the evidence is not enough.
